## 〇、检视结论摘要（Executive Summary）

针对 08 号架构演进草案的系统性深度审计，主要结论如下：

1. **核心价值肯定**：
   该方案精准命中 07 号重构落地后的三大数据库物理瓶颈——**逐文件全量覆盖明细引发的写放大**、**大事务包裹高耗时 Matching 占满连接池并阻断 Autovacuum 回收死元组**、以及**缺乏数据库维度的历史快照清理归档机制**。提出“稀疏存储”、“读写解耦短事务”和“TTL 分级生命周期”的技术方向完全正确。
2. **致命隐患定级（Request Changes）**：
   该方案在业务语义闭环、数据模型依赖链及并发一致性机制上存在严重盲区与副作用：
   * **工作台空洞化（盲台账）**：误以为 `defects` 是完全自包含实体，TTL 物理删除历史 `observations` 与 `findings` 将直接导致前端治理工作台和缺陷详情的标题、描述、代码片段全为空白；
   * **存量缺陷自愈卡死与局部扫描误判**：稀疏落库剪枝了未变更文件，导致对账判定器获取为 `nil`，存量缺陷被误判未覆盖而死锁在 `COVERAGE_GAP`，无法闭环推进；
   * **并发乐观锁雪崩**：解耦后 Phase 1 读快照到 Phase 3 提交期间缺乏排他保护与冲突重试机制，并发扫描将高频抛出 `defect %d changed during ledger commit`；
   * **重试回滚误杀存量缺陷与别名**：快照物理清理会导致重试回滚中的统计值归零，触发存量缺陷与别名的硬删除（Unscoped Delete）。
3. **裁决建议**：
   **禁止当前草案直接进入编码落地**。必须按照本报告提出的“Defect 模型文本冗余”、“ScopeCoverageEvaluator 接口抽象”、“Matching 乐观锁重试循环”及“别名计数解耦”等 6 项架构加固措施修订 08 号文档后重新评审。

## 一、潜在副作用深度剖析（5 大关键副作用）

### 1.1 副作用一：前端治理工作台“盲台账/空洞化”灾难（严重）

* **设计缺陷**：文档在 §5.1 将 `AnalysisFinding` 和 `defect_observations` 归类为 Tier 3（轮次事实快照），建议在“30 天 / 最近 10 轮”后批量物理删除，认为 `defects` 属 Tier 1 会永久保留。
* **代码证据**：
  查验现网模型 [`models/models.go:1038-1076`](file:///home/fugui/codes/code-shield/models/models.go#L1038)，`Defect` 表仅包含指纹、行号范围、哈希与治理状态：
  ```go
  type Defect struct {
      ID                   uint   `gorm:"primaryKey"`
      RepoID               uint   `gorm:"not null;uniqueIndex:uq_defects_current_identity"`
      CanonicalFingerprint string `gorm:"size:64;not null;uniqueIndex:uq_defects_current_identity"`
      NormPath             string `gorm:"size:512;not null"`
      Status               string `gorm:"size:32;not null;default:'ACTIVE'"`
      // ... 仅有指纹、哈希、行号，无任何文本描述 ...
  }
  ```
  缺陷的真实标题（`Title`）、详细说明（`Detail`）、代码片段（`CodeSnippet`）与修复建议（`Suggestion`）**完全存放在 `AnalysisFinding` 中**。
* **连锁破坏**：
  查验 [`services/defectlifecycle/workbench.go:120-189`](file:///home/fugui/codes/code-shield/services/defectlifecycle/workbench.go#L120) 的 `projectWorkbenchPayload`，治理工作台加载缺陷列表完全依赖链式联查：
  $$\text{Defect (ID)} \longrightarrow \text{DefectObservation (最新 ReportID + GroupUID)} \longrightarrow \text{AnalysisFinding (文本详情)}$$
  若将历史 `defect_observations` 和 `AnalysisFinding` 物理删除：
  任何早于 30 天前检出且当前仍在治理中的存量缺陷（如低危缺陷或排期处理缺陷），在前端工作台及缺陷详情页（`GetDefectDetail`）展示时，**其标题、代码片段、描述和建议全部为空**！活跃工作台将直接沦为无法读懂的“空壳幽灵台账”。

### 1.2 副作用二：稀疏存储导致“存量缺陷自愈推进卡死”与“局部扫描误判”（严重）

* **设计缺陷**：
  文档 §3.2 提出仅将 `FAILED`、`diff_touched=true` 以及 `has_findings=true` 的文件写入稀疏表，并在 §4.2 伪代码中直接将 `sparseEntries` 传递给 `commitLedgerOptimized`。
* **代码证据**：
  查验对账状态机推进代码 [`services/defectlifecycle/ledger.go:641-642`](file:///home/fugui/codes/code-shield/services/defectlifecycle/ledger.go#L641)：
  ```go
  scope := scopeEntryByPath(input.Scope, defect.NormPath)
  covered := scope != nil && scope.Outcome == ScopeScanned
  ```
* **连锁破坏**：
  1. **存量缺陷自愈卡死**：假设存量缺陷所在的文件本轮未被修改（`diff_touched=false`），无失败且代码已修复（本轮未再报出，即 `has_findings=false`）。按照稀疏规则，该文件**不会被记录在 `sparseEntries` 中**。引擎在 `scopeEntryByPath` 中获取为 `nil`，从而判定 `covered = false`。该存量缺陷直接被误判为“文件未覆盖”，转入 `COVERAGE_GAP`，**永远无法推进至 `RESOLVED` 或 `DORMANT`，自愈机制彻底停摆**！
  2. **局部扫描误判修复**：文档 §3.3 的 `ScopeCoverageIndex` 仅记录了 `FailedFiles`，判定规则为“非明确失败即覆盖”。若执行针对部分模块的局部扫描（如仅扫描 `pkg/auth/`），未纳入扫描计划的 `pkg/api/` 文件因不在 `FailedFiles` 中，会被错误地判定为已覆盖，**导致未扫描区域的存量缺陷被错误判定为已修复**，彻底破坏了 07 重构方案的核心安全红线（I1/I2 原则）。

### 1.3 副作用三：读写解耦后的并发冲突与乐观锁雪崩

* **设计缺陷**：
  文档 §4.1 将流程重构为 Phase 1（无锁读快照） $\to$ Phase 2（纯内存 Matching，耗时 20~150ms） $\to$ Phase 3（短事务原子写）。
* **代码证据**：
  当前系统在 [`services/defectlifecycle/ledger.go:263-269`](file:///home/fugui/codes/code-shield/services/defectlifecycle/ledger.go#L263) 中依赖 PostgreSQL Transaction Advisory Lock（`SELECT pg_advisory_xact_lock(...)`），将同一仓库的对账入库严格串行化。
* **连锁破坏**：
  一旦 Matching 移出互斥锁且未设串行队列保护，若同代码仓存在并发扫描任务（如开发者连续快速推送两次 Git Commit，或手动重试与定时扫描并发）：
  1. 任务 A 与任务 B 在 Phase 1 同时读取了相同的 `defects` 快照（此时均为 `row_version = 1`）；
  2. 任务 A 纯内存计算后先进入 Phase 3 提交，缺陷升级为 `row_version = 2`；
  3. 任务 B 随后进入 Phase 3，在执行 `ledger.go:587` 乐观锁校验时：
     ```go
     query := tx.Model(&models.Defect{}).Where("id = ? AND row_version = ?", defect.ID, defect.RowVersion)
     ```
     由于数据库中 `row_version` 已变为 2，`query.RowsAffected == 0`，直接触发 panic 级报错：
     `defect %d changed during ledger commit`，整个任务落库崩溃中断！
  文档完全缺少乐观锁冲突重试循环（Retry Loop）或调度层仓级单飞保护。

### 1.4 副作用四：异步写 Manifest（`go saveScopeManifestAsync`）导致数据丢失与悬挂脏数据

* **设计缺陷**：
  文档 §4.2 伪代码中使用 `go saveScopeManifestAsync(input.Report.ID, manifestData)` 进行异步落盘。
* **连锁破坏**：
  1. **快照丢失**：若系统遇到容器重启、发版替换或 OOM，未完成落盘的协程直接销毁。由于数据库中仅存稀疏明细，该报告对应的全量文件清单将**永久丢失**且无法重建；
  2. **悬挂脏文件**：若 Phase 3 数据库短事务因约束冲突回滚，而异步文件已写入磁盘或对象存储，将产生无法关联的悬挂孤儿垃圾文件。

### 1.5 副作用五：历史快照物理清理引发“重试回滚级联误删”与“自愈别名清零”

* **代码证据**：
  1. [`ledger.go:324-345`](file:///home/fugui/codes/code-shield/services/defectlifecycle/ledger.go#L324)：`rollbackReportLedger` 在重新扫描回滚时，会统计同缺陷在其他轮次的观测记录：
     ```go
     tx.Model(&models.DefectObservation{}).Where("defect_id = ? AND report_id <> ?", defectID, report.ID).Count(&otherCount)
     ```
     若早于 30 天前的 `defect_observations` 被 TTL 删光，`otherCount` 变为 0，系统会误认为该缺陷是该报告首次独占生成的，从而触发 `tx.Unscoped().Delete(&models.Defect{}, defectID)`，**导致历史存量缺陷被物理硬删除**！
  2. [`ledger.go:379-395`](file:///home/fugui/codes/code-shield/services/defectlifecycle/ledger.go#L379)：`recomputeAffectedAliases` 依赖 `SELECT COUNT(*) FROM defect_observations WHERE defect_id = ?`。历史观测被删后 `count = 0`，系统会**误判该别名已无观测支撑并将其从 `defect_aliases` 中删除**，造成后续 K1/K2/F1 别名自愈能力永久失效！
  3. [`campaign.go:471-484`](file:///home/fugui/codes/code-shield/services/defectlifecycle/campaign.go#L471)：专项治理战役在计算覆盖率时直接对 `scan_scope_entries` 表进行 `Count` 查询。历史快照被清理后，专项治理将无法回溯历史轮次的修复准入事实。

## 二、对现有系统数据的影响有哪些？

| 维度 | 具体影响表现 | 潜在风险与应对要求 |
| :--- | :--- | :--- |
| **物理存储与表结构** | `scan_scope_entries` 写入行数缩减 95% 以上，PostgreSQL WAL 生成速率和 Dead Tuples 堆积大幅放缓。 | **数据断层**：老报告存有全量数千行，新报告仅存数十行。上层业务代码不能再假设“查该表必能查出代码仓内任意未变更文件”。 |

## 三、设计完善度评估与 6 大设计盲区

### 3.1 盲区一：台账主体（`defects`）缺少核心文本元数据的自给自足
* **问题**：设计草案假定 `defects` 永久保存即可保障治理平台运作，忽视了缺陷标题、描述、代码片段全部分散在 `AnalysisFinding` 的现状。
* **完善要求**：必须在 `defects` 模型中冗余持久化首次发现或最新确认的文本信息，实现单表自给自足。

### 3.2 盲区二：生命周期判定引擎与底层物理存储强耦合
* **问题**：直接将落库剪枝后的 `sparseEntries` 当作对账判别器的输入，混淆了“物理落库稀疏优化”与“逻辑覆盖全面核验”的边界。
* **完善要求**：生命周期引擎必须面向抽象接口 `ScopeCoverageEvaluator`，由内存基于 Planned Files 完整集装配，完全与数据库是否稀疏存储解耦。

### 3.3 盲区三：长事务解耦后的并发一致性方案缺失
* **问题**：草案只提出将 Matching 移出写事务，未对 Phase 1 快照读到 Phase 3 提交期间的并发修改（`row_version` 冲突）提供重试保障。
* **完善要求**：在调度器层实施仓级单飞队列（`singleflight`），并在持久化层增加带指数退避的乐观锁重试循环（Matching Retry Loop）。

### 3.4 盲区四：Manifest 文件归档缺少两阶段原子落盘机制
* **问题**：使用裸协程 `go saveScopeManifestAsync`，无法应对进程意外中止与事务回滚产生悬挂文件的情况。
* **完善要求**：实施“事务前预写临时文件 $\to$ 事务提交成功 $\to$ 原子 Rename 转正”的 2PC 本地事务机制。

### 3.5 盲区五：TTL 清理算法对既有机制缺乏安全护栏
* **问题**：未考虑历史清理后对重试回滚（`rollbackReportLedger`）和别名命中统计（`recomputeAffectedAliases`）的破坏性连锁反应。
* **完善要求**：别名命中计数改为每轮原子递增（解耦全局 Count 回算）；回滚逻辑增加超期保护阻断。

### 3.6 盲区六：多数据库方言与测试环境兼容性不足
* **问题**：硬编码 PostgreSQL 专有语法（如 `SET idle_in_transaction_session_timeout`、`VACUUM (ANALYZE)`），可能破坏 SQLite 单测环境（如 `testdb.SetupIsolatedDB`）。
* **完善要求**：所有方言级参数加固必须包裹严格的 `if db.Dialector.Name() == "postgres"` 校验，并对 SQLite 环境提供 No-op 平替。

### 4.2 方案修正二：抽象统一的 `ScopeCoverageEvaluator` 接口

解耦生命周期判定与物理落库：

```go
// ScopeCoverageEvaluator 统一定义生命周期对账的覆盖判定契约
type ScopeCoverageEvaluator interface {
    // IsCovered 精确判断文件是否在本次扫描的计划且成功覆盖范围内
    IsCovered(normPath string) bool
    // IsChanged 判断文件本轮是否被 Git Diff 触碰（代码变更）
    IsChanged(normPath string) bool
    // IsFailed 判断文件是否处理失败（返回失败标识及失败原因）
    IsFailed(normPath string) (bool, string)
}

// MemoryScopeEvaluator 基于全量计划文件构建的内存高性能判定器
type MemoryScopeEvaluator struct {
    plannedFiles map[string]bool   // 全量计划文件集合
    failedFiles  map[string]string // 失败文件及错误原因
    touchedFiles map[string]bool   // diff_touched 文件
}

func (e *MemoryScopeEvaluator) IsCovered(normPath string) bool {
    if _, failed := e.failedFiles[normPath]; failed {
        return false
    }
    return e.plannedFiles[normPath]
}

func (e *MemoryScopeEvaluator) IsChanged(normPath string) bool {
    return e.touchedFiles[normPath]
}

func (e *MemoryScopeEvaluator) IsFailed(normPath string) (bool, string) {
    reason, failed := e.failedFiles[normPath]
    return failed, reason
}
```

在生命周期状态机推进中，一律使用 `evaluator.IsCovered(defect.NormPath)` 代替直接在稀疏条目列表中检索。

### 4.3 方案修正三：三阶段解耦流水线与乐观锁重试循环

重构后的持久化主逻辑：

```go
func PersistScanFactsOptimized(input ScanInput) (*ScanFactsResult, error) {
    // 1. 内存中构建全量计划覆盖判定器（对账专用）与稀疏入库切片（存储专用）
    fullScopeEntries := buildScopeEntries(input)
    evaluator := NewMemoryScopeEvaluator(input, fullScopeEntries)
    sparseEntries, manifestBytes := filterSparseScope(input, fullScopeEntries)

    // 2. 事务前将 Manifest 写入临时文件（两阶段落盘准备）
    tempManifestPath, err := writeTempManifest(input.Report.ID, manifestBytes)
    if err != nil {
        return nil, fmt.Errorf("write temp manifest: %w", err)
    }
    defer os.Remove(tempManifestPath) // 若未 Commit 或出错则自动清理

    // 3. 带指数退避的乐观锁并发重试循环
    const maxRetries = 3
    var lastErr error

    for attempt := 1; attempt <= maxRetries; attempt++ {
        // ── Phase 1: 无锁快照读 ──
        defects, aliases, err := loadSnapshot(input.DB, input.Repo.ID, input.TaskType.ID)
        if err != nil {
            return nil, err
        }

        // ── Phase 2: 纯内存匹配计算（零 DB 锁占用） ──
        matching := RunMatching(MatchingInput{
            Observations: ledgerGroups,
            Defects:      defects,
            Aliases:      aliases,
            Budget:       RuntimeMatchBudget(),
            Thresholds:   RuntimeMatchThresholds(),
        })
        decisions := buildDecisions(matching, groups, input)

        // ── Phase 3: 极简短事务提交（<15ms） ──
        var result *ScanFactsResult
        txErr := input.DB.Transaction(func(tx *gorm.DB) error {
            // 批量写稀疏覆盖清单
            if len(sparseEntries) > 0 {
                if err := persistSparseScope(tx, sparseEntries); err != nil {
                    return err
                }
            }
            // 提交台账流转（内部使用 evaluator 进行覆盖判定，使用 row_version 控制并发）
            ledgerRes, err := commitLedgerOptimized(tx, groups, decisions, evaluator, input)
            if err != nil {
                return err
            }
            result = ledgerRes
            return nil
        })

        if txErr == nil {
            // 事务提交成功，原子 Rename 将 Manifest 正式转正
            if err := finalizeManifest(input.Report.ID, tempManifestPath); err != nil {
                log.Printf("[Warn] Finalize manifest failed for report %d: %v", input.Report.ID, err)
            }
            return result, nil
        }

        // 若为乐观锁版本冲突，休眠退避后重试
        if errors.Is(txErr, ErrDefectVersionConflict) {
            lastErr = txErr
            time.Sleep(time.Duration(attempt*50) * time.Millisecond)
            continue
        }
        return nil, txErr
    }

    return nil, fmt.Errorf("commit scan facts conflict after %d retries: %w", maxRetries, lastErr)
}
```
