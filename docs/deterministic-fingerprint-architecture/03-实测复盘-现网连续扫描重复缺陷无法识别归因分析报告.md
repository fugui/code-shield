> **专题归属**：CodeShield 确定性源码指纹与抗抖动增量生命周期架构 (Deterministic Fingerprint Architecture)  
> **文档性质**：现网真实扫描实测归因与脱敏复盘基线 (Benchmark Empirical Analysis)  
> **业务脱敏说明**：本报告对所涉及的具体工程代码仓名称、业务模块路径、专有命名空间及业务私有符号均已进行标准化抽象脱敏，保留全部真实的缺陷模式、LLM 输出抖动数据、字段对比指标与算法推导逻辑。

> **分析对象**：同一生产代码仓 PROJ_CORE (脱敏) 的两次扫描报告
> - Report 1：`2026-09-02/report-19334-synthesis-PROJ_CORE.json`（122 条问题）
> - Report 2：`2026-09-03/report-19355-synthesis-PROJ_CORE.json`（137 条问题）
>
> **分析日期**：2026-09-03

## 1. 现象概述

两次扫描间隔仅 1 天，代码仓 PROJ_CORE 几乎没有变更。按照预期，第二次扫描中的绝大多数问题应被标记为 `EXISTED`（已存在），只有少量真正新增的问题标记为 `NEW`。

**实际情况**：

| 指标 | Report 1 (09-02) | Report 2 (09-03) |
|------|:-----------------:|:-----------------:|
| 问题总数 | 122 | 137 |
| `diff_status = NEW` | 111 (91%) | 128 (93%) |
| `diff_status = EXISTED` | 11 (9%) | 9 (7%) |
| **两报告间 fingerprint 交集** | **0** | **0** |

几乎所有问题都被标记为"新问题"，fingerprint 在两份报告间 **完全没有交集**。这意味着当前的重复识别机制完全失效。

### 3.3 trigger_line 代码片段截取不一致

同一行代码在两次扫描中被截取为不同长度、不同格式的片段。

#### 案例 1：不同行被选为触发行

**文件**：`proj_measurement/srv_shc/src/main.cpp`

| 报告 | trigger_line |
|------|---|
| R1 | `Common::Logger::Info()("CoreServer exit normal! signal = %d", signal);` |
| R2 | `SignalHandlerRegister([](int signal) -> void { Common::Logger::Info()(...); CoreFramework::Destroy(); exit(signal); });` |

R1 选择了信号处理函数内部的 `Logger::Info()` 调用作为触发行，R2 选择了整个 `SignalHandlerRegister` lambda 注册语句。两者描述的是同一个信号处理安全问题。

#### 案例 2：多行 vs 单行

**文件**：`proj_facility/dev_gui/appui/gui/src/main.cpp`（信号处理函数）

| 报告 | trigger_line |
|------|---|
| R1 | `strings = backtrace_symbols(buffer, nptrs);\n    ...\n    free` |
| R2 | `strings = backtrace_symbols(buffer, nptrs); free(strings);` |

R1 截取了多行片段（含换行和省略），R2 压缩为单行。

#### 案例 3：同行但缩进不同

**文件**：`proj_measurement/vmc/src/StateConvertManager.cpp`

| 报告 | trigger_line |
|------|---|
| R1 | `if (m_curState->GetStateType() == state) {\n        return SYS_STATUS_OK;\n    }` |
| R2 | `if (m_curState->GetStateType() == state) { return SYS_STATUS_OK; }` |

```python
# R1 规范化后（空白合并）
"if (m_curState->GetStateType() == state) { return SYS_STATUS_OK; }"
# R2
"if (m_curState->GetStateType() == state) { return SYS_STATUS_OK; }"
# 结果：完全相同！
```

本案例在空白规范化后其实是一致的。但实际中 R2 的 trigger_line 选了同函数内另一行 `std::thread convertThread(...)`，说明触发行选择本身不稳定。

#### 案例 4：同一函数内不同触发点

**文件**：`proj_measurement/cam_yag/src/ImageUploadTask.cpp`，函数 `HighFreqImageUploadTask::Encode`

| 报告 | trigger_line | category |
|------|---|---|
| R1 | `auto uploadImageData = ConvertImageDatasToUploadDatas(imageData); ... m_encodeOu` | `内存管理问题-空指针解引用` |
| R2 | `m_encodeOutputs.emplace(imageData->timestamp(), uploadImageData);` | `内存管理问题-空指针解引用` |

两行代码相邻（R1 第 216 行，R2 紧跟其后），描述的是同一个空指针解引用风险——只是 LLM 选择了函数内不同的行作为"触发点"。

### 3.5 title/detail/suggestion 由 LLM 自由生成

在 22 组确认的重复问题对中，`title` 和 `detail` 的 **100% 不一致**——每次 LLM 都会用不同的措辞描述同一个问题。

### 3.6 code_snippet 缩进差异

即使是同一段代码，`code_snippet` 字段在不同报告中也有缩进差异：

**文件**：`mod_proc/src/DataProcessor.cpp`，函数 `RecalculateStatistics`

```
# R1 code_snippet（无前导缩进）
size_t size = m_data.size();
for (size_t i = 0; i < size; i++) {
    m_sum += m_data[i];
    ...

# R2 code_snippet（有 4 空格前导缩进）
```

## 4. 二次效应：扫描覆盖范围不稳定

除了字段级别的不一致，两次扫描覆盖的文件范围本身就有显著差异。

| 指标 | 数量 |
|------|:----:|
| 仅在 R1 出现的文件 | 43 个（含 51 条问题） |
| 仅在 R2 出现的文件 | 38 个（含 45 条问题） |
| 两次共有的文件 | 56 个 |

约 **35% 的问题所在文件**只在一次扫描中出现。这意味着即使 fingerprint 完美，这些文件中的问题也会被标记为"新"——因为上次根本没有扫描到。

## 5. diff_status 可靠性分析

### 5.1 diff_status 判定逻辑推断

`diff_status` 字段标记为 `NEW` 或 `EXISTED`，应当反映问题是否在上次扫描中已存在。由于 fingerprint 在两报告间交集为 0，`EXISTED` 标记只能来自报告内部的某种模糊匹配或与前序基线的匹配。

### 5.2 22 组确认重复对中的 diff_status 一致性

| R1 diff_status | R2 diff_status | 数量 | 评价 |
|:--------------:|:--------------:|:----:|------|
| NEW | NEW | 14 | 两次都未识别为已存在 — **均错误** |
| **EXISTED** | **NEW** | **5** | R1 正确识别为已存在，R2 错误标为新 — **R2 diff 失效** |
| **NEW** | **EXISTED** | **3** | R1 错误标为新，R2 正确识别为已存在 — **R1 diff 失效** |
| EXISTED | EXISTED | 0 | 没有一对是两次都正确识别的 |

**关键发现**：没有一组重复问题在两次扫描中都被正确标记为 `EXISTED`。有 5 组问题在 R1 中被正确标记为 `EXISTED`，但在 R2 中被错误标记为 `NEW`——这说明 `diff_status` 的判定不仅跨报告不可靠，连同一问题在不同时间的判定结果都会翻转。

## 7. 改进建议

### 建议 1：fingerprint 算法重构 — 只用确定性字段（P0）

**当前问题**：fingerprint 似乎包含了 LLM 生成的自由文本（title/detail/category 等），导致每次扫描都不同。

**改进方案**：fingerprint 应仅基于 **源码确定性行为**，不包含任何 LLM 生成内容：

```
fingerprint = sha256(
    normalized_file_path +        // 仓库相对路径，去除临时目录前缀
    normalized_scope_symbol +     // 见建议 2
    normalized_trigger_line +     // 见建议 3
    normalized_category_code      // 见建议 4，使用枚举而非自由文本
)
```

**关键原则**：只要源码未变，fingerprint 就不应变。所有由 LLM 生成的自由文本字段（title、detail、suggestion、hunter_claim、challenger_arg、judge_verdict）一律不参与 fingerprint 计算。

### 建议 2：scope_symbol 规范化（P1）

**当前问题**：命名空间前缀有时有有时无，lambda/函数运算符描述方式不同。

**改进方案**：

- 从 AST/编译器符号信息提取，不依赖 LLM 描述
- 规范化规则：去除所有命名空间前缀，只保留 `Class::Method` 或 `Function` 的最核心部分（取最后 2 段）
- 对 lambda/匿名函数，使用统一格式如 `enclosing_function::<lambda>`，不使用 `operator()(signal handler)` 等自然语言
- 对多个函数合并的报告，按函数名排序后用固定分隔符拼接

```python
def normalize_scope_symbol(s: str) -> str:
    """规范化 scope_symbol，去除命名空间前缀差异"""
    if not s:
        return ""
    # 处理多函数合并的情况：按 ' / ' 分割，各自规范化后排序拼接
    parts = s.split(" / ")
    normalized = []
    for part in parts:
        segments = part.strip().split("::")
        # 取最后 2 段（Class::Method 或 Method）
        core = "::".join(segments[-2:]) if len(segments) >= 2 else segments[-1]
        normalized.append(core)
    return " / ".join(sorted(normalized))
```

### 建议 3：trigger_line 规范化（P1）

**当前问题**：代码片段截取长度、换行处理、缩进不一致；同一函数内不同行被选为触发行。

**改进方案**：

- trigger_line 应精确到**单行代码**（触发问题的那一行），而非多行片段
- 规范化处理：去除所有空白字符差异、去除尾部分号、统一缩进

```python
def normalize_trigger_line(t: str) -> str:
    """规范化 trigger_line，消除空白和格式差异"""
    if not t:
        return ""
    # 如果是多行，只取第一行（或最核心的那一行）
    lines = t.strip().split("\n")
    # 选择最长的那一行作为代表（通常是真正的触发行）
    main_line = max(lines, key=len).strip()
    # 合并多余空白
    main_line = " ".join(main_line.split())
    # 去除尾部分号
    main_line = main_line.rstrip(";").strip()
    return main_line
```

- 如果需要多行上下文，放在 `code_snippet` 字段，不参与 fingerprint
- `code_snippet` 参与指纹计算时，需先做缩进归一化（dedent）

### 建议 4：category 改为受控枚举（P0）

**当前问题**：~100 种自由文本分类，中英文混用，粒度不一，同一问题可能被归入完全不同的类别。

**改进方案**：定义固定的分类枚举，LLM 只能从中选择：

```python
# 受控分类枚举
CATEGORIES = {
    "NULL_DEREF",          # 空指针解引用
    "OOB_READ",            # 越界读
    "OOB_WRITE",           # 越界写
    "UAF",                 # 释放后使用
    "DOUBLE_FREE",         # 双重释放
    "RACE_CONDITION",      # 数据竞争
    "SIGNAL_SAFETY",       # 信号处理不安全
    "DEADLOCK",            # 死锁
    "MEM_LEAK",            # 内存泄漏
    "UNINIT_VAR",          # 未初始化变量
    "UNCAUGHT_EXCEPTION",  # 未捕获异常
    "STACK_OVERFLOW",      # 栈溢出
    "TYPE_CONFUSION",      # 类型混淆
    "DIV_BY_ZERO",         # 除零错误
    "INVALID_ENUM",        # 非法枚举值
    "USE_AFTER_SCOPE",     # 作用域后使用
    "RESOURCE_EXHAUST",    # 资源耗尽
    "LOGIC_ERROR",         # 逻辑错误
    # ... 按需扩展
}
```

- 在 prompt 中明确要求 LLM 只能从上述列表中选择 `category`
- 后端对 LLM 输出做校验，不在枚举中的值拒绝或归入最近的类别
- 保留原始 LLM 自由文本作为 `category_detail` 字段供人阅读，但不参与 fingerprint

### 建议 5：line_number 确保非空且单一格式（P1）

**当前问题**：R2 有 20 条空 line_number；多段格式不一致。

**改进方案**：

- **禁止空 line_number**：如果无法确定行号，至少给出 `trigger_line` 所在行；可通过在源码中搜索 `trigger_line` 内容来反查行号
- 统一格式为 `start_line-end_line`（单行时 start==end）
- 行号范围应以 `trigger_line` 所在行为锚点，而非整个函数体——建议固定为 `trigger_line` 所在行 ± 0（即单行），或最多扩展到所在语句块
- 多段行号 `102-103, 158-186` 的格式应改为拆分为多个独立问题，或统一取首个行号段

### 建议 6：引入多级匹配策略做 diff_status（P2）

即便 fingerprint 完美，也应有 fallback 匹配机制作为兜底：

```
Level 1: fingerprint 精确匹配 → EXISTED（高置信度）
Level 2: (file_path, normalized_scope_symbol, normalized_trigger_line, category_code) 匹配 → EXISTED（高置信度）
Level 3: (file_path, normalized_scope_symbol, category_code) + 行号距离 ≤ 5 → EXISTED（中置信度，需人工确认）
Level 4: (file_path, normalized_scope_symbol) 匹配 + LLM 语义相似 → LIKELY_EXISTED（低置信度，需人工确认）
Level 5: 以上都不匹配 → NEW
```

### 建议 7：稳定扫描覆盖范围（P2）

**当前问题**：约 35% 的问题所在文件只在一次扫描中出现。

**改进方案**：

上游的分块（chunking）逻辑需要确保：

- **同一文件在两次扫描中一定会被分析**（或一定不被分析）——扫描范围应由配置文件或文件列表决定，不由运行时动态决定
- **分块边界稳定**：以函数/类为单位分块，并以 AST 确定的函数签名作为 chunk 标识，而非按固定行数切割
- **记录扫描范围日志**：每次扫描产出一份"已扫描文件/函数清单"，便于对比两次扫描的覆盖差异

### 建议 8：二次去重 — 语义相似度匹配（P3）

对于 fingerprint 未匹配但语义相同的"漏网之鱼"，可以用 embedding 相似度做二次去重：

```python
# 伪代码
for issue_r2 in report_2:
    if issue_r2.diff_status == "NEW":
        # 构造语义指纹
        text = f"{issue_r2.file_path} {issue_r2.scope_symbol} {issue_r2.trigger_line}"
        embedding = embed(text)
        # 与 report_1 中所有问题的 embedding 做余弦相似度
        for issue_r1 in report_1:
            sim = cosine_similarity(embedding, issue_r1.embedding)
            if sim > 0.85:
                issue_r2.diff_status = "LIKELY_DUPLICATE"
                issue_r2.duplicate_of = issue_r1.id
                break
```

- 对 `(file_path, trigger_line, title)` 组合做 embedding
- 计算跨报告的余弦相似度
- 相似度 > 0.85 的对标记为 `LIKELY_DUPLICATE`，供人工确认

### 建议 9：severity 评估稳定性（P3）

**当前问题**：同一问题在两次扫描中 severity 可能不同（如 Match 9 中从"严重"变为"建议"）。

**改进方案**：

- severity 应由 `calibration_rule`（已基本一致）驱动，`calibration_rule` 与 `severity` 的映射关系固定化：

```python
RULE_TO_SEVERITY = {
    "RULE_CRASH_DETERMINISTIC":          "致命",
    "RULE_MEM_CORRUPTION_DEFAULT_REACHABLE": "严重",
    "RULE_ARCH_STYLE_SUGGESTION":        "建议",
    "RULE_RESOURCE_DOS_OR_FLAKY":        "一般",
}
```

- 当前两份报告中 `calibration_rule` 的分布高度一致（R1: 56/45/15/6, R2: 70/47/16/4），说明 calibration_rule 本身较稳定，severity 应直接从规则推导而非由 LLM 独立判断

## 8. 优先级排序

| 优先级 | 建议 | 预期效果 | 实现难度 |
|:------:|------|----------|:--------:|
| **P0** | 建议 1: fingerprint 只用确定性字段 | 直接解决"0 匹配"问题 | 低 |
| **P0** | 建议 4: category 受控枚举 | 消除分类不一致对 fingerprint 的污染 | 低 |
| **P1** | 建议 2: scope_symbol 规范化 | 消除命名空间前缀不一致（从 20→36 匹配） | 中 |
| **P1** | 建议 3: trigger_line 规范化 | 消除代码片段截取差异 | 中 |
| **P1** | 建议 5: line_number 非空+统一格式 | 消除 20 个空行号问题和格式差异 | 低 |
| **P2** | 建议 7: 稳定扫描覆盖范围 | 消除 35% 的文件级差异 | 高 |
| **P2** | 建议 6: 多级匹配策略 | 提高容错性，作为 fingerprint 的兜底 | 中 |
| **P3** | 建议 8: embedding 二次去重 | 兜底方案，捕获所有漏网之鱼 | 中 |
| **P3** | 建议 9: severity 从规则推导 | 消除严重等级评估不一致 | 低 |

### 预期改进效果量化

| 改进阶段 | 预期 fingerprint 匹配数 | 预期 diff_status 准确率 |
|----------|:----------------------:|:----------------------:|
| 当前 | 0/137 (0%) | ~7% |
| 完成 P0（fingerprint + category） | ~22/137 (16%) | ~25% |
| 完成 P1（scope + trigger + line） | ~36/137 (26%) | ~40% |
| 完成 P2（覆盖范围 + 多级匹配） | ~50+/137 (36%+) | ~60%+ |
| 完成 P3（embedding + severity） | ~60+/137 (44%+) | ~75%+ |

> 注：剩余的 ~40% 真实新增问题（来自 R2 新增文件、新发现的问题等）会被正确标记为 NEW，这是预期行为。
